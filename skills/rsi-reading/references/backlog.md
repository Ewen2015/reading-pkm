# 改进项队列

**这是队列，不是许愿单。** 每条都要有证据、成本、可证伪的验收标准。
没有证据的条目要么补证据，要么删掉——留着会污染判断。

状态取值：`open`（待做）｜`trialing`（在试）｜`adopted`（已采纳）｜`rejected`（否掉）｜`blocked`（等外部）

每条还要标一个**维度**，因为 S4 是分支（见 [`loop-map.md`](loop-map.md)）：

- `内容` —— 笔记与卡片本身（与渠道无关）
- `呈现` —— 同一份内容在不同载体上好不好读
- `渠道` —— 分发到哪、各渠道的规则与指标
- `取用` —— 书库被检索与引用
- `回流` —— 数据从出口流回决策
- `工程` —— 路径、归档、埋点这类地基

排序依据：证据强度 × 对北极星的影响 ÷ 成本。**一次只动一条。**
**改 S4 时必须写明作用在哪一维**，否则又要把载体/渠道/呈现焊死在一起。

## R17 · 桥接依赖漂移（websockets 必须 13.1）

状态：open
记录：2026-10-05
维度：工程 · 渠道

**证据**：2026-10-05 07:49 `rednote-post` 桥接整体不可用——`xhs.py status` 报
「bridge server 未运行 / 浏览器扩展未连接」，而 Chrome 里扩展和登录都正常。
根因是 `/tmp/xhs-skills-repo/.venv` 里 `websockets` 从锁定的 13.1 漂到了 16.0；
换回 13.1 后立刻「扩展已连接」。`publishing.md` 早就写了这个坑，但只在
`setup_bridge.sh` 里安装时锁一次——环境一旦被重建（uv 重解析、venv 重建、`/tmp`
被清理后重跑）就会静默失效，而报出来的错象是「扩展没装好」，很误导。

### R36 · 长正文 `fill` 撞 300s 上限后，页面停在半成品态且没有自愈路径

状态：**已修复（代码级，附回归测试；2026-10-06 第三次遭遇时收口）**
记录：2026-10-06
维度：呈现 · 发布（S3）

**证据（流程内发现）**：本轮 `fill` 在 08:38:42 开始，08:43:42 报
`Bridge 错误: 命令执行超时（300s）`（`input_content_editable` 那一步），`fill` 整体失败。
但页面**不是空的**：标题 ✓、5 张图 ✓、正文已有 812/883 字（归一化后），
断在倒数第二行（出版信息那行），标签行完全没进去。也就是说失败留下的是**半成品**，
既不能重跑 `fill`（文档明说会填两遍），也没有一条"接着填"的路径。

三条次生证据，都比超时本身值钱：
1. **300s 是擦边过的，不是余量。** 上一个样本（《思维的囚徒》，993 字 + 8 标签）`fill`
   花了 ≈5 分钟**跑通**；本轮 960 字 + 8 标签恰好撞线。同一个命令、量级相当的正文，
   一次过、一次不过——说明预算就在边缘上，不是"偶发网络慢"。
2. **CLI 放弃之后，浏览器侧还在打字。** 08:43:42 CLI 已报超时，08:43:40 页面正文还在增长；
   到 ≈08:47 我读到的正文仍停在"…中文世界。"，而我自己追加那行之后，**同一行出现了两次**。
   时间线能对上的是：浏览器侧那次打字没有随 CLI 超时而停止，和我后来的写入撞在了一起。
   （这一条**只有时间线证据，没有抓到执行体**，所以只记现象，不断言机制。）
3. **可修复性其实很好。** 剩下没填的只有两行。用 `evaluate` 把断掉的那行插进去、
   再单独跑 `xhs.py tags`（标签本来就有独立子命令），页面就完整了；`verify` 回读一致。
   所以缺的不是能力，是**编排**：没有"从半成品接着填"的第三条路径。

**根因（第 3 次遭遇时定位到，前两次都记成了"正文太长"）**：不是正文太长，是
**`CMD_TIMEOUT` 在 server 进程启动时读一次就定死**，而服务器进程经常早就起好了。
一个用旧默认（300s）起着的常驻 server 占着 9333，之后每条 CLI 都连到它、拿到 300s——
此时在 shell 里写 `XHS_CMD_TIMEOUT=900 python3 xhs.py fill` **一点用都没有**，
因为环境变量属于调用方，不属于那个已经在跑的进程。前两次的"擦边"其实是同一个旧进程。

这也解释了样本 #3/#4 里那条最反直觉的证据：**量级相当的正文，一次过、一次不过**。
不是预算在边缘上抖，是"这次连上的是哪个 server"在变。

**修复（落地在本项目，不在上游补丁里）**：
- `bridge_server.py` 的 `ping_server` 回报本进程实际生效的 `cmd_timeout`；
- `xhs.py` 的 `ensure_server` 拿它和需要的值比，**不够就杀掉端口上那个
  `bridge_server.py` 再起一个**（`_kill_port_owner` 只杀命令行含 `bridge_server.py` 的进程——
  `lsof -ti tcp:9333` 也列出客户端，按 pid 直杀会连自己一起带走）；
- 换完 server 会等扩展重连（最多 25s）——**换 server 自带"Extension 未连接"这个新故障**，
  不等它就会在紧接着的第一条命令上撞；
- `xhs.py status` 把 `命令上限 : 900s` 打出来，不足时直接标注。

**验收（已通过，2026-10-06）**：故意用 `XHS_CMD_TIMEOUT=120` 起一个 server →
`status` 打印「命令上限 : 120s ← 低于 900s…」→ `reset` 打印「停掉旧 bridge server（pid …）」
并正常完成 → `status` 打印「命令上限 : 900s」。回归步骤写进了
`skills/rednote-post/references/publishing.md`。

**实测效果**：本样本 `reset`+`fill`+`verify` 合计 **≈100s**（含 5 张图上传、734 字正文、
8 个话题标签），`fill` 不再有超时风险。相比样本 #3/#4 各烧掉 5 分钟且毫无产出，
这一项直接省下 ≈5 分钟并去掉了"半成品态"这个需要人工判断的分支。

**仍未做**：`fill` 仍然不是**可续跑**的。修复只是把撞墙概率压到很低，
没有提供"从半成品接着填"的第三条路径。若将来正文长到 900s 也不够，同一个半成品态会回来。
真要收口，得让 `fill` 在开始时探测页面是不是半成品并在其基础上继续填。

**假设**：`fill` 的正文这一步不该有一个**按正文长度算不出来的固定上限**。
两条互斥的改法，先试哪条要按数据选：
(a) 把 `XHS_CMD_TIMEOUT` 默认值从 300s 提到足够余量（成本≈0，但只是把墙往后挪）；
(b) 让 `fill` 正文改成**分段提交 + 断点续填**——先读回页面已有正文，算出还缺哪一段，
只补那一段（成本中，但把"超时"从失败降级成可恢复）。
更根本的问题是打字为什么这么慢：`cmdInputContentEditable` 是**逐行** insertText、
行间只 sleep 40ms，理论上 50 行≈2s，实测却是分钟级——**怀疑是后台标签页被节流**，
但这是猜测，需要一次前台/后台对照实验才能确认。

**最小试验（待做）**：同一份正文，比较"标签页在前台"与"标签页在后台"两种情况下
`input_content_editable` 的墙钟耗时。若是节流，改法就不该是加超时，而是**发布时把标签页带到前台**
（或改成分段提交，让每段都短到不受节流影响）。

**验收**：960 字以上正文 + 8 标签的一次 `fill`，在后台标签页下要么一次跑通、
要么失败后能一条命令接着填完；不再出现"必须人工补 DOM"。

**成本**：低（加超时）／中（分段续填）

**观察**：新记。这一条和 R35 是同一族——**命令的成功判据与页面事实脱钩**：
R35 是"报成功其实没落地"，这条是"报失败其实做了一半"。两次都是**半成品状态没有名字**，
于是只能靠人（这次是模型）读页面才知道停在哪。

**观察（2026-10-06 第二次复现 · 四条新证据）**：本轮《成本与选择》1000 字正文 + 8 标签，
`fill` 再次撞 300s，撞点逐字相同（`input_content_editable`）。上一轮的三条猜测这轮被进一步收窄：

1. **（a）改法有个隐藏前提，之前没写出来。** `XHS_CMD_TIMEOUT` 是**两侧都读**的：
   CLI 侧 `bridge.py` 读它当 socket 超时，**服务端 `bridge_server.py` 也在启动时读一次**
   （`CMD_TIMEOUT = float(os.environ.get("XHS_CMD_TIMEOUT", "300"))`）。
   已经在跑的 bridge server 是默认 300s 起的，所以**在调用方的 shell 里设 `XHS_CMD_TIMEOUT=600` 完全不起作用**
   ——本轮就是这么设的，照样 300s 死。想走 (a)，要么重启 bridge server 时带上环境变量，
   要么把默认值写死改大。**"加个环境变量就能解决"是假的，除非连服务端一起重启。**
2. **打字慢不再是首要嫌疑。** 本轮量了一次对照：把缺的 3 段（约 170 字，含 3 次
   `insertParagraph` + 段间 90/150ms sleep）用一次 `evaluate` 补齐，**墙钟 5.37s**；
   把 9 行纯 `insertText` 灌进同一段，**≈0.0s 返回**。
   编辑器在这个规模上根本不慢——所以 300s 不是"逐字插入的成本"堆出来的，
   **"标签页被节流/计时器被冻结"这条假设相对变强**（但测量时刻页面自报
   `visibilityState=visible / hidden=false / hasFocus=false`，说明"可见但窗口无焦点"，
   和"隐藏被节流"对不上，仍未有定论）。
3. **`verify` 的回读会低报，不能用它判断"断在哪"。** 本轮 `verify` 说正文停在
   「…不给工具。」（页面 687 / 本地 882），但直接读 `editor.innerText` 是 **870 字**，
   且下一段「它还有三条没论证的前提…」**其实已经在页面上了**。
   我照着 `verify` 那份过期快照去补，结果**把这一段补成了两遍**。
   所以半成品态的定位必须**直接读 DOM**（`[contenteditable][role=textbox]` 的 `innerText`），
   `verify` 只能用来判"够不够长"，不能用来判"断在哪个字"。
4. **`tags` 会把标签行劈成两段并混入一段正文。** 手工补完之后跑 `xhs.py tags`，
   结果 8 个话题分落两个 `<p>`，且第一个 `<p>` 尾部多出一段正文文字
   （「🔍 顺藤摸瓜」）——`_input_tags` 回填时按 `querySelectorAll("p")` 的全局下标定位
   "正文最后一段"，在半成品态下这个下标是错的，于是把光标放回了正文中部。
   （本轮用 `Range` 跨段删除修好了，8 个话题仍全部生效。）
   **这条和 #3 同源：所有"按段落下标定位"的收尾命令，在半成品态下都不安全。**

**半成品态的定位，更新后的正确姿势**：先读 `innerText` 拿真实尾巴 → 只补尾部 →
再跑 `tags` → 读 `innerText` 复查话题是否只有一个 `<p>`。

### R40 · 状态扫描会**静悄悄少报**，并把"没读全"报成"读完了"

状态：已修复（代码级 + 现场验收，附回归步骤）
记录：2026-10-06
维度：度量（S0／S3 之间的观测面）

**用户回一句"已确认还在平台定时队列里"——整个结论反了。**

这不是平台丢笔记，是本 skill 的观测面在说谎。**它污染的是整条闭环的输入**：
排期缺口、覆盖率、要不要补一篇、最佳时段，全都建立在"看到的队列就是全部队列"之上。

**根因（三层，缺一层都不会犯）**：
1. 笔记管理是**虚拟滚动**，首屏只挂约 10 张，往下要靠滚动触发下一页请求。
2. **滚动滚错了元素**：`page.scroll_to_bottom()` 滚的是 window，而 window 根本滚不动
   （`scrollHeight == clientHeight`，实测全是 923）——真正的容器是 `.note-card` 的可滚动
   祖先 `.list-container-box` / `.microapp-container`。所以滚动是**彻底的 no-op**。
3. 于是"连续 3 次卡片数不变"被当成"列表到底"（`scroll_exhausted = true`）。
   而**页面此时还挂着「正在加载」**——真正的原因是 Chrome 窗口不在前台
   （`document.hasFocus() = false`，`outerHeight: 0`），**下一页请求压根没发出去**。

现场取证（都做过了，可复现）：hook `fetch`/`XHR` 后反复滚动，**没有任何 `posted?page=1` 请求**；
`visibilityState: visible` 但 `hasFocus: false`；等 64s 卡片数恒为 10；
直接 `fetch` 列表 API 返回 `{"code":-1}`（缺签名头，此路不通）。

**为什么危险**：它不报错、不缺字段，`scroll_exhausted: true` 看上去就是"扫全了"。
**"少读"和"读完"在输出上完全同形。**

**修复（已落地 `rednote-assistant`）**：
- `SCROLL_JS` 改为滚 `.note-card` 的可滚动祖先（+ 派发 `scroll` 事件），不再依赖 window。
- `scroll_and_collect` 返回三元组 `(卡片, exhausted, partial)`：**页面还显示「正在加载」时
  一律不算 exhausted**；`partial` 单独报出来。
- `scan_queue` 增加 `partial` / `expected_total`（从 tab 标签「全部 255」解析）/ `window_focused`；
  拿到卡片数少于标签总数时也判 partial。
- `emit` 在 stderr 打醒目警告（走 stderr 是为了不弄脏 stdout 的 JSON），
  **并直接给出可执行的处理**："把 Chrome 切到前台重扫"。
- `plan.py report` 的平台状态段会带出 ⚠️ 行，明确写"下面的缺口与覆盖率都不可信"。
- `SKILL.md` 铁律 4/5 + `references/plan-schema.md` 新增「先确认它是'全部'，再拿它判断」。

**回归测法**：把 Chrome 切到后台，跑 `xhs_state.py queue --max 60`，
应看到 `scroll_exhausted: false`、`partial: true`、`expected_total: 255`，
且 stderr 打出「Chrome 窗口不在前台」——**旧版这里输出的是 `scroll_exhausted: true` 且一片安静**。

**还没解决的**：`hasFocus` 这条路我这边没法自己满足（`osascript` 激活 Chrome 后
`document.hasFocus()` 仍是 false，窗口很可能被最小化或不在当前 Space）。
**「切到前台」这条也验了，结果是没用。** 2026-10-06 本轮又试了一次：
`osascript` 把 Chrome 顶到最前、窗口从屏幕外恢复（`outerHeight` 由 0 → 923）、

所以「把窗口切到前台」作为处方**不成立**，R40 输出的提示语要改成这条。

而 `_looks_uninformative`（只认哈希串、纯数字、长度<2）**不认这个占位名**，
于是它被当成一个真实著录，**优先于从文件名洗出来的「谈谈方法」**，一路用到改名和登记。

**为什么危险**：改的是**用户交来的那个文件本身**（当 `--into` 就是文件所在目录时
`src.parent == outdir`，走的是 `rename` 而不是 `copy`），而且**没有修理路径**——
`queue set` 的补丁字段只有 `status/author/file/note`，**改不了书名**（见 R48）。
这一次是我手工改 JSON + `os.replace` 恢复的。

**修法**（已落进 `skills/book-fetch/scripts/fetch.py`）：把 `clean_filename` 补出来的占位名
（`未命名` / `book` / `untitled`）纳入 `_looks_uninformative`——占位名不是著录。
一行常量表 + 一行判断。

**验收**：`adopt` 同一份 PDF 时，书名应为「谈谈方法」（来自文件名），文件名为
`谈谈方法.pdf` / `谈谈方法 - 笛卡尔.pdf`，队列书名不再是「未命名」。
已验证（用一份副本在 `/tmp` 上重跑 adopt）。

**顺带记下这一轮的教训**：这个 bug 是 `670dff9`（给 epub 加"著录优先于文件名"）
引入的**回归**——那一次的规则对 epub 是对的，对"根本没有著录的 pdf"是错的。
**"没有著录"和"著录叫这个名字"必须走不同的分支**，这正是这一轮踩的那一脚。

## R47 · 扫描件的探测只看"有没有文字层"，不看"能不能用"

状态：open（**样本 #11 第二次复现，仍未工具化**）
记录：2026-10-07
维度：S1 取得书 · S2 阅读

**第二个样本（2026-10-07，样本 #11）**：`通向奴役之路` 交来的是 278 页 PDF，
探测报 **370 字/页**（阈值 50），于是被放行；`extract_book_text.py` 10 秒抽完、
看起来一切正常。但文字层是十几年前的老 OCR，错字成系统：`真理的末曰`→末日、
`熱矣於集體行動`→热衷、`少有人尊東`→尊重、`願怠違反`→愿意违反，还夹着孤立的
拉丁字母（`AQ`、`S`）和零星的简化字。**又是人读出来的，不是工具报出来的。**
改走 Vision 重 OCR（278 页；渲染 39s + OCR 149s）后才可用。

**两个样本的共同点**：探测只看"有没有字"，不看"这些字对不对"。**R47 至今未工具化。**

**证据（第一个样本）**：`谈谈方法` 这份 PDF 是 2006 年 Adobe Paper Capture 的 OCR，
**文字层存在**（`ocr_scanned_pdf.py` 的探测读到 556 字/页，远高于 `MIN_CHARS_PER_PAGE = 50`），
所以默认路径不会重 OCR。但它的错字**成系统**：

| 旧文字层 | 正确 | 旧文字层 | 正确 |
| --- | --- | --- | --- |
| 筒卡尔 | 笛卡尔 | 先人之见 | 先入之见 |
| 没高办法 | 没有办法 | 形而L学 | 形而上学 |
| 图书在版编自 | 图书在版编目 | 半角 ，； 混排 | 全角 |

改成 macOS Vision 重 OCR（`ocr_scanned_pdf.py --force`，133 页 / 250dpi / **96 秒**）
之后，上面每一处都对了，且全角标点统一。两份文本量级相当
（83,817 字 vs 85,085 字）——**差别不在多少，在对错**。

**为什么是问题**：这一条链的下游是**引用**。正文和卡片都要写原句，
而"笛卡尔"被识成"筒卡尔"这种错误，凭常识能改；
`清楚分明`／`磐石和硬土` 这类关键短语一旦被识错，改起来要靠回看扫描图，
而**没有人会去回看**——错误会静默地进入笔记和发布物。

**假设**：可用的判据不止"字数"。至少有三条现成的、不需要读懂内容的信号：
① PDF 元数据里 `producer` 命中 `Paper Capture`／`ABBYY`／`OCR`；
② 同一页内**半角/全角标点混用**（`；` 与 `;` 并存）；
③ 抽样页里的**字符可疑率**（CJK 之外的孤立字母、`l`/`1`/`I` 互换、罕见的 CJK 兼容字）。

**最小试验**：给 `ocr_scanned_pdf.py` 的 `--probe-only` 加一段"文字层质量"报告——
报 producer、报全角/半角混用率、报抽样页的 ASCII 噪声比，
并把结论落成一句话建议（"建议 --force 重 OCR"或"文字层可用"）。
**只加报告，不自动改行为**，先跑 5 本已知的书看它说对没有。

**验收**：在这份 PDF 上报"建议重 OCR"，在《成本与选择》（无文字层的扫描件，
本来就该 OCR）与一本正常 epub 转出的 PDF 上都不误报。

**成本**：低到中（探测逻辑 + 一次 5 本的回归）。
**收益**：把"要不要重 OCR"从"看运气"变成"看报告"。

## R67 · 合并是**键级**的：段还在，值被一个更差的扫描整段换掉（R52 的下一层）

状态：open
记录：2026-10-09
维度：回流 · 工程

**证据（本轮连锁，两个动作串起来的）**：R52 修完 `emit()` 之后，`state.json` 的**段**不再丢。
但 2026-10-09 21:16 的例行收尾是这样坏的：

1. `xhs_state.py queue --out state/queue-20261009d.json` → 40 张卡片、**14 条定时档**（含刚发的
   12:30 那档），与 20:37 的全量读一致；
2. 紧接着按惯例跑 `xhs_state.py all --out state/state.json` → 撞上平台限流，queue **只读到 10 张卡片**、
   `partial: true`。写进文件时 `merge_into_file` 是 `{**old, **payload}`：`queue` 这个键在，
   **值被整段换掉**。`state.json` 里的定时档从 14 条掉回 **3 条**。

**根因**：R52 修的是"段被抹掉"，合并粒度是**键**。可扫描的输出有**质量档位**
（`cards_scanned` / `partial` / `scroll_exhausted`），同一段的新值**可以比旧值差**。
现有逻辑只判"这次扫了没有"，不判"这次扫得比上次好吗"。

**为什么危险**：`state.json` 是 `plan.py ready --state` 的输入。3 条定时档会让
`ready` 认为 10-11→10-19 是空的 —— **排期结论直接反向**（对着一个已经排满的窗口说"有空档"）。
和 R40／R52 同族，但更隐蔽：数据没丢、时间戳是新的、`partial: true` 也确实在文件里，
**只有一个"没人读的字段"在说它不可信**。

**最小试验（本轮已人工兜底，未改码）**：用 `state/queue-20261009d.json` 回填 `state.json` 的 `queue`。
真正要做的：合并时同一段**按质量取优**——`partial: false` 优先于 `partial: true`；
同为 `partial: true` 时 `cards_scanned` 大者胜；输的那次只更新元信息（或记进一个 `previous`）。
判据全在已有字段里，不用新增采集。

**验收**：① 种一个 `partial: false` / 40 张的 `queue`，跑一次只读到 10 张的 `all --out`，
