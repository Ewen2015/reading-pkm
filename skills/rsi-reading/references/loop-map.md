## 关键修正：S4 是分支，不是节点

小红书**不是**这条链上的一个环节，它是 S4 里的一种实现：

- **本质**：把 reading notes 渲染成某种 **UI**，再分发到某个**渠道**。
- **现在**：只跑通了「图文卡片 → 小红书（公开社交）」这一条路径。
- **可能性**：同一份素材可以同时扇出成多种 UI——
  one-pager HTML（`scandinavian-style` 已经在做）、打印版、长文、播客稿、
  以及 `second-brain` 回答里的**对话式呈现**（那也是一种 UI 与消费方式）。

所以 S4 的设计问题不是"小红书笔记怎么做"，而是三个正交的维度：

| 维度 | 取值（现状加可能） |
| --- | --- |
| 载体 | 图文卡片（已跑通）· 单页 HTML（已跑通）· 长文 · 打印版 · 音频/对话 |
| 渠道 | 公开社交：小红书（唯一在用的）· 私域（朋友/群）· 自用（笔记、日记） |
| 呈现 | 版式、字号、信息密度、封面、强调方式 |

**当前把这三层压在了一个地方**：`rednote-post` 同时承担"选内容"、"排版式"、"发小红书"。
小红书只是渠道维度的一个取值，但它的平台约束（标题 ≤ 20 字、正文 ≤ 1000 字、
最多 18 图、网页编辑器不能加粗）已经渗进了内容层。

**内容层现在有两道闸门**（2026-10-07 起，R57）：`render_cards.py` 判**版式**
（溢出／压页脚／字号／孤字换行），`check_content.py` 判**内容**
（半成品标记／加粗／强调色／封面素材／版本唯一），两者都被 `plan.py ready` 收进发布就绪闸门。
在此之前，内容层规则只写在散文里，没有任何自动化在查——**规则从散文里重新推导，
就是这条链最容易发生的内容退化**。

**渠道侧新加的一条**（2026-10-07，R60）：`plan.py ready` 多了「空档在平台定时窗口内」。
小红书的定时发布只收「今天 + 13 天」以内的时刻，而超窗**不报错**——表单回读仍是你填的值，
平台存下的却是它自己的默认值（"今天 + 1 小时"）。所以"排期成功"这件事也有了两层判据：
闸门判**排不排得进窗口**，`xhs.py verify-scheduled` 判**平台到底存了什么**。
**回读要读平台的落库结果，不要读自己写进去的那个字段。**

**2026-10-08 补两条**（R61、R62）：
- 窗口是**按日期**截断（今天 + 13 天），**不是**滚动 13×24 小时——今天 20:52 提交 10-21 22:00
  成功，滚动口径下应当失败。`plan.py` 的判据还停留在 datetime（R62，open）。
- 窗口内没有主线空档时，**不再"压着成品等窗口往前滚"**。2026-10-08 先加了 `fallback_slots` 兜底，
  2026-10-09 换成更简单的一条（R66 取代 R61）：`cadence.slots` 直接写两档（12:30 / 22:00），
  `ready` **取最近的那个空档**。代价照旧——落到白天档的那天等于发两条，会互相分流。

**2026-10-08 再补四条**（R63、R64、R65、R49）：
- **观测仪以前看不见成品**：`rsi.py` 只扫 `<workspace>/published` 与 `Documents/*/xhs-post`，
  漏了 `plan-schema.md` 写明的成品目录 `posts/`。后果是**系统性地少算成品**（对账表 17 → 修后 19），
  并把一篇已经做完的成品报成"有卡片但没做过成品"。已修（R63）。
- **S3（沉淀）与 S4（分发）之间没有闸门**：成品可以上线，而书根本没进书库——
  今天正是修完 R63 才照出《Tiny Habits》的**孤儿产物**（R64）。
  观测仪的「孤儿产物」一栏就是为这个建的，修完 R63 才第一次有内容。

  否则卡在库里、`recall` 却取不出来（今天 5 句自然问法命中 0 句）。见 R65。

  于是报出两个假断点。这是 R49 的老问题被 R63 重新照亮。

## 两条断掉的回流边

### 回流 A：渠道反馈 → 呈现与选题（**2026-10-11 起半通**）

原来 `state/state.json` 里躺着 19 条数据却没有一处消费它。2026-10-11 接上了第一段
（R3，trialing）：

- **数据源换成了创作服务平台的数据看板**（比 `state.json` 厚得多，而且**分位是同类归一化的**，
  原始比率在几十观看量下全是噪声）；落地在 [`skills/rednote-post/scripts/analytics.py`](../../../skills/rednote-post/scripts/analytics.py)。
- **选题**：`copywriting.md` 新增「本账号实测：角度决定收藏」——按**收藏率**排序，
  导出定角度的两句闸门（读者此刻的具体毛病 + 书里命名它的机制）。
- **封面**：`cards.md` 新增「封面是唯一被平台判"有待提升"的一环」——同类诊断 3/3 封面点击率
  低于中位数，而内容丰富度 3/3 是同类前 1%。（属性未知 → R70。）

**还没接上的**：

- `topics.md` 的选题池仍然不看数据（R1 未解）；
- `plan.json` 里唯一用上数据的还是 22:00 这个时段（5 篇样本）；2026-10-08 加的兜底档 12:30
  **不是数据结论**，是 `timing.md` 的基线（自有数据白天档每档只有 1 篇）；
- 快照靠手动 `fetch`，没人定时抓 → **会像 `state.json` 一样腐烂**（R71）。

而且这条边**天然是分渠道的**：小红书有阅读/收藏，私域有回复，自用渠道根本没有指标。
现在把"反馈"和"小红书"绑死了——将来加渠道，这条边必须拆成按渠道各算各的。

### 回流 B：用到的卡 → 书库取舍（断）

`second-brain` 名义上是这条链的终点（"输出是下一次思考时的 skill 插入"），但它不回话：

- 没有 recall 日志 → 不知道哪些卡被读过；
- 不知道哪些卡**从没被任何问题命中过**（死卡）；
- 不知道哪些问题反复落空（书库缺口）。

代价：**书库只增不减、只凭感觉补。**

   会先出载体、后补 durable 笔记，于是**发出去的那一版不受第二大脑那份笔记约束**。
   见 backlog R45。

## 这条流水线的目标（写下来，别默认）

不是"每周发 7 篇小红书"。是**把读过的书变成下次思考时真正会被调用的视角**——
分发是让它被调用、并拿到反馈的手段之一，不是终点。

北极星：**被真正取用的思想密度**。
"取用"发生在所有出口上——小红书有人收藏是取用，`second-brain` 回答里被引用也是取用，
one-pager 被人读完还是取用。现在的度量只看得见第一个出口。

推论：
- 补检索日志（R2）优先于一切美化类改进——它打开的是**看不见的那个出口**。
- 任何 S4 的改进项都要标明它作用于哪个维度（载体／渠道／呈现），否则会再次把三层焊死。
